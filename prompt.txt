### 1. 🔴 Critical: WSS 接続認証に「裏口」が 2 つ（実測）

`src/sockets/socket.index.js` の `io.use()` 内で

- `token.startsWith('demo-jwt-token-')` → JWT 検証&#x3092;__&#x5B8C;全スキッ&#x30D7;__&#x3057;て `TEACHER` として接続許可
- `jwt.verify` 失敗時、`NODE_ENV !== 'production'` なら __`dev-user`（TEACHER）として接続を許可__（`console.warn` だけ）

`.env` は `NODE_ENV=development` なので、実サーバーで実測した結果：

```javascript
tokenless            => REJECTED: Token missing          ← 正しく弾かれた
garbage-token        => CONNECTED  chat:send ack={"success":true,... sender_id:"dev-user"}
demo-token           => CONNECTED  chat:send ack={"success":true,... sender_id:"demo-teacher"}
cross-origin+garbage => CONNECTED  chat:send ack={"success":true,...}
```

つまり __`wss://0.0.0.0:3443` に任意の token（有効な JWT 不要）で接続でき、職員全体チャンネルへの書き込みができる__（Origin も無制限、`src/server.js:60` の socket.io cors は `parseCorsOrigin(...,'*')`、`.env` の `CLIENT_ORIGIN=*`）。

さらに socket ハンドラーには権限チェックがありません:

- `seating:update_status` は role 判定なしで `authService.updateStatus()` を呼ぶ（`src/sockets/seating.socket.js:20-38`）
- `lock:acquire / release / timeout_released` は `resourceType/resourceId` を文字列のまま受け取り DB 書き込み（`src/sockets/lock.socket.js:20-141`）

__対策__: デモ分岐を削除、`jwt.verify` 失敗は常に `next(new Error(...))`、`NODE_ENV=production` で稼働、socket 側にも `requireKyomu` 相当の role gate と `socket.handshake.headers.origin` の許可リスト照合を追加。

### 2. 🔴 Critical: JWT シークレットが既知の既定値、かつ他機密のキーも兼ねている（実測）

  ```javascript
  FORGED-ADMIN /api/auth/me    => 200
  FORGED-ADMIN /api/audit/logs => 200 （監査ログ全件）
  FORGED-ADMIN /api/users      => 200 （全教職員一覧）
  ```

- 派生被害: `src/models/mail.model.js:13-15` は __AES-256-GCM のキーを `sha256(jwtSecret)` から導&#x51FA;__&#x3057;ています。つまり secret を知る者&#x306F;__&#x6559;職員のメールパスワードを全件復&#x53F7;__&#x3067;きます。

- `src/services/auth.service.js:20-22,32` に SHA-256(password + secret) フォールバック、さらに `storedHash === password`（__平文パスワード一致__）が残っています。

__対策__: 強随机 secret（`crypto.randomBytes(32)`）+ 環境ごとに個別化、メール暗号キーは別系統（KMS / scrypt + 専用秘密）で分離、平文比較と SHA-256 フォールバック削除、key rotation 手順。

### 4. 🔴 High: ログイン試行制限・アカウントロックが一切ない（実測）

`grep -rniE 'rate.?limit|express-rate' src/ package.json` → __該当ゼロ__。実測:

```javascript
存在しないユーザー T9999999 への 25 回失敗ログイン => 401 ×25（ロックも 429 もなし）
実在ユーザー T2026001 への 10 並列失敗           => 401 ×10
```

加えて __招待コードは 8 桁 16 進__（`auth.service.js:248` `crypto.randomBytes(4)`）で有効期限 24 時間、試行制限なし。4.29 億通り、レート制限なしの環境では総当たりが現実的で、`register-invitation` はパスワード再設定にも使えるた&#x3081;__&#x30A2;カウント乗っ取&#x308A;__&#x306B;直結します。失敗ログインは監査ログに記録されません（成功 `LOGIN` のみ、`auth.service.js:102`）。

__対策__: `express-rate-limit` を `/api/auth/login`・`/api/auth/register-invitation` に適用（IP + 識別子キー、15分 5 回）、ユーザー単位ロックアウト、失敗時 `LOGIN_FAILED` を監査ログへ、招待コードは 128bit 系（`randomBytes(16)`）+ 試行カウンタ。

### 6. 🟠 Medium: CSP 無効 + SRI なし CDN + CORS ワイルドカード（実測）

- `src/app.js:26` → アプリ側で `contentSecurityPolicy: false`（HTTP CA ページには CSP あり）。HTTPS レスポンスヘッダに CSP &#x306F;__&#x51FA;ません__。
- `public/index.html:9,10,13` → `cdn.tailwindcss.com`・`unpkg.com/lucide`・`cdn.socket.io/4.7.5` を __`integrity`（SRI）なし・`crossorigin` な&#x3057;__&#x3067;読み込み。CDN 改変・パスジャックで任意スクリプトが実行可能。
- トークンは `localStorage['is_system_jwt_token_v251']`（`public/js/config.js:74`、`public/js/socket.js:34`）→ XSS で即座に盗める。
- 実測: `Origin: https://evil.example` → `Access-Control-Allow-Origin: *` + __`Access-Control-Allow-Credentials: true`__（`CLIENT_ORIGIN=*`）。Cookie は使いませんが、** Authorization ヘッダ方式なので、盗んだ token を任意サイトから使える**構造です。
- `data-lucide="${ch.icon}"`・`iconEl.setAttribute('data-lucide', channelInfo.icon)` は DB 由来値&#x3092;__&#x7121;escapeで属性に埋め込み__（`chat.module.js:649, 813`）→ 属性注入の余地。

__対策__: CSP（`script-src 'self'`＋許可 CDN、SRI 付与、socket.io は自前 vendoring）、`CLIENT_ORIGIN` をカンマ区切り明示リスト（`parseCorsOrigin` はリスト対応済み）、wildcard 時は `credentials: false`、icon 値も escape。

### 7. 🟠 Medium: ログアウトが実体を伴わない（JWT に失効機構なし）

実測: `POST /api/auth/logout` &#x306E;__&#x540C;じ token がそのまま 200__ を返します（`auth.controller.js:306-315` は 200 を返すだけ）。`expiresIn: '24h'`（`config/default.js:68`）。token が漏れた場合、24 時間取り消せません。

__対策__: token ブラックリスト（Redis/DB）＋ logout で削除、TTL を短く（15–30分）+ refresh、可能なら httpOnly Secure Cookie セッション。

### 8. 🟠 Medium: 自己署名 CA の信頼配布が TOFU、失効手段がない

CA を各クライアント&#x306B;__&#x5E73;文 HTTP（0.0.0.0:3000）で配&#x5E03;__&#x3059;る構成（`server.js:95-101`）は、初回取得時に CA 差し替え攻撃を受け得ます（コンソールに SHA-256 指紋 `A2:E5:...:DC` を表示しており指紋ピンチングは可能＝好ましい）。サーバー鍵が漏れた際の __CRL/OCSP がな&#x3044;__&#x305F;め、クライアントは気づけません。CA 鍵がサーバーと同じマシンにある点も運用リスクです。

__対策__: CA 配布を管理端末に限定（`INSECURE_HOST` を 127.0.0.1 や校内限定 VLAN に）、指紋を事前共有、CRL 発行＋クライアント側検証、CA 鍵を別マシン/HSM に分離。

### 9. 🟡 Minor: コード品質に起因する認証の隙

- 監視ホストが両ポート `0.0.0.0` → LAN 全体に公開（1 と相乗効果で「LAN 内の誰でも dev-user として書ける」）。

次に出張等の登録を行う。調査開始ボタンを押すと、自分を含めた全員に実施日の氷河表示され、出張等で欠席するコマを登録できるようになる。
調査終了ボタンを押して調査を終了するが、教務権限者のみ以降も編集可能とする。
最後に監督割の作成を行う。１教室に監督１人が配置されるようにする。「非常勤の出勤可能なコマの登録」「非常勤のコマ条件（１日１コマ、２時間連続可、３時間連続可、２時間連続不可等）の登録（個別）」「英語コミュニケーションは１コマ前の時間をリスニング準備として空けておかなければならない」「発展化学等は単独で実施している科目なので、出題者と監督を同じ先生が担当する」「教務の中で別室１、予備１を回さなければならない」「別室２は３学年で担当し、次の時間は空きでなければならない」「数学Ⅲは後半の監督を担当する人は前の時間が空きでなければならない」「可能なら出題者は回答受け取りがあるため、出題の次の時間はあける」「非常勤を除いて、試験日のうち１日は出題・監督がない日をつくらなければならない」「非常勤を除いて、全員が同程度、コマが埋まっていなければならない」等の条件を設定できるようにする。
監督割ができたら。公表開始ボタンを押すと全員に表示され、個々が自由に編集できるようになる。
公表終了ボタンを押して調査を終了するが、教務権限者のみ以降も編集可能とする。

時間割作成の教務画面では、様々な条件に対応するために、コマの作成が必要です。
